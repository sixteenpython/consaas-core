# Feature ID

NARRATIVE-001

# Title

Validate AI-proposed narrative statements before canonical persistence

# Product

Narrative Architect

# Feature Type

Architecture-enabling product feature

# User Story

As an author, I want the system to distinguish my facts from its interpretations so I can trust and revise canonical story memory.

# User Problem

Probabilistic JSON could otherwise be stored as author truth or lose its supporting screenplay evidence.

# Business / Product Objective

Establish trustworthy canonical memory before conversational creation begins.

# Context

The NKA is canonical; chat and model output are not. Local models remain replaceable and non-authoritative.

# Existing Capability

Architecture and ADRs define epistemic/provenance principles, but no executable validation boundary previously existed.

# Proposed Capability

Typed statements, explicit epistemic status, evidence references, model-run provenance, fail-closed validation, and a separate author-assertion path.

# Knowledge Asset Impact

Defines the smallest knowledge-bearing unit later NKA aggregates reference.

# Decision Intelligence Impact

None yet; it protects later extraction and interpretation outputs before they influence decisions.

# Deterministic Components

Schema/key validation, status rules, evidence/confidence checks, identifier assignment, and serialization.

# LLM / AI Components

Not implemented in this slice. Future local models produce raw statements that pass this gate.

# Inputs

Untrusted structured model data or an explicit author field/value assertion.

# Outputs

Typed immutable statement or an explicit validation error.

# Provenance Requirements

Model statements require model-run ID; extracted/inferred statements require artifact and span references.

# Versioning Requirements

Schema version is explicit; breaking changes require migration and compatibility review.

# Dependencies

Core AI contracts and the evaluation convention.

# Architecture Impact

Narrative domain logic consumes Core contracts. It is not promoted to Core without two-product evidence and an ADR.

# Core Reuse Candidates

Epistemic statement validation is a candidate only; it remains Narrative-specific today.

# Acceptance Criteria

1. A model cannot create `user_asserted` content.
2. Extracted and inferred statements without evidence fail.
3. Inferences without confidence or any model statement without run ID fail.
4. Confidence outside zero-to-one and contract drift fail closed.
5. Canonical IDs are generated by deterministic code.
6. User assertions contain no fabricated model metadata.
7. Tests and offline evaluation cover accepted and rejected paths.

# Test Requirements

Unit tests cover valid inference, missing fields, false author claims, absent evidence, confidence validation, and user assertions; an integration smoke test crosses Core registry to Narrative validation.

# AI Evaluation Requirements

Versioned offline cases exercise grounded inference, ungrounded inference, and model-authored user claims without calling a model.

# Security / Privacy Considerations

Inputs are untrusted, screenplay text stays local, and evidence stores identifiers rather than duplicating content.

# Observability Requirements

Future integration counts accepted/rejected statements by reason and run ID without content logging.

# Explicitly Out of Scope

Chat, persistence database, full NKA, compiler/parser, SDI diagnosis, UI, and actual model invocation.

# Definition of Done

Acceptance criteria, tests, evaluation, all quality gates, documentation, review, and CI evidence pass.

# Implementation Notes

Keep the raw-output-to-validation-to-canonical sequence explicit; never let adapters persist domain state.

# Suggested Task Breakdown

One vertical task, `NARRATIVE-001-T01`, implements the typed boundary, tests, evaluation, and documentation.
